# AGENTS.md

## Project overview

**Invita** is a digital wedding invitation platform with two audiences:

1. **Product landing page** (`/`) — sells the service to engaged couples in Spanish. Marketing copy, zero technical jargon.
2. **Admin panel** (`/admin`) — private tool used only by the business owner to manage client invitations, RSVPs, and leads.
3. **Public invitations** (`/[slug]`) — the actual wedding invitation page delivered to each couple's guests, rendered from data stored per invitation.

Current business model: manual/service-based. The owner loads each client's data herself through the admin panel — there is no self-service client editor yet. Do not build a self-service flow unless explicitly asked.

## Tech stack

- Next.js (App Router) + TypeScript
- Tailwind CSS
- Framer Motion (animations, used on the landing and public invitations — not required in the admin)
- TanStack Query + Axios (client-side data fetching for the admin)
- Zod (all form and API input validation)
- Postgres via Supabase (database + auth + storage)
- Vercel (hosting)

Do not introduce a different state management library, CSS framework, or backend runtime without asking — these choices are deliberate and already validated against the owner's existing skill set.

## Commands

```
pnpm run dev       # start local dev server
pnpm run build     # production build
pnpm run typecheck # next typegen && tsc --noEmit
```

`next typegen` before `tsc` is deliberate: route types (`LayoutProps`, `PageProps`) are generated by Next, so `tsc` on its own under-reports problems in route files.

`pnpm run lint` is not wired up yet — Next.js 16 removed `next lint`, and `eslint.config.mjs` is already in the repo, but `eslint` + `eslint-config-next` are not installed. Install those dev dependencies and add the script in the same change; never add a `lint` script that cannot run.

Note that `next.config.mjs` sets `typescript.ignoreBuildErrors: true`, so `pnpm run build` will not catch type errors. Run `pnpm run typecheck` before considering a change done.

## Design system

Use these tokens **only** on the product landing page and public invitation pages. The admin panel should stay visually neutral (e.g. shadcn/ui defaults) — it's a tool for the owner, not a branded surface.

- Colors: forest green `#1F3A2E` (primary), ivory `#FBF8F2` (background), aged gold `#B08D57` (accent), ink `#1A1A17` (text), sage green `#8FA396` (secondary text on dark backgrounds)
- Typography: Fraunces for display/headers, a calligraphic script (e.g. Mrs Saint Delafield or italic Cormorant Garamond) reserved for couple names only, Inter for body/UI text
- Motion principle: one deliberate "hero" animation moment (e.g. the envelope-opening gate) may pulse or animate without user input; everything else should be triggered by scroll or explicit user action — avoid generic fade-in-on-every-section patterns
- Explicitly avoid: cream+terracotta gradient backgrounds, rounded cards with identical generic gray drop shadows, uppercase eyebrow labels stacked above every single heading
- Tokens live in `app/globals.css` under `@theme`, namespaced (`forest`/`ivory`/`paper`/`gold`/`sage`/`ink`/`wine`/`line`) so they can never shadow the neutral shadcn/ui palette the admin relies on. Fonts are wired through `next/font` in `app/layout.tsx` (`font-display`, `font-editorial`, `font-body`). Reusable utilities defined there: `gold-foil-border`, `botanical-glow`, `paper-texture`, `hairline-gold`. The type scale and the `text-label-caps` style also come from `@theme`. The only self-running animation is the `--animate-seal-glow` token (used as `motion-safe:animate-seal-glow motion-reduce:animate-none`) on the hero's wax-seal mockup
- The eyebrow-over-heading pattern is allowed, but never centred and identical on every section — vary alignments and skip it where the composition does not need it
- Favicon and app icons come from Next's **file convention**, not from `metadata.icons`: `app/favicon.ico` is the real multi-size icon (PNG frames at 16/32/48/64/128/256), `app/icon.png` (512×512) and `app/apple-icon.png` (180×180) sit next to it, and Next emits every `<link rel="icon">` itself — all three are drawn from the brand mark `public/invita-logo.png`. Never declare `metadata.icons` entries pointing at files that do not exist — the browser 404s on that link instead of falling back to the favicon

## Data model

Postgres schema — treat as the source of truth. Don't rename fields or restructure tables without confirming first.

```sql
invitations (id, slug, template_id, status, couple_a, couple_b,
  wedding_date, intro_text, hero_photo_url, quote, dress_code_label,
  dress_code_note, gift_note, gift_bank_titular, gift_bank_banco,
  gift_bank_cuenta, allow_kids, rsvp_deadline, created_at)

invitation_photos (id, invitation_id, url, order)
schedule_items (id, invitation_id, time, label, icon, order)
locations (id, invitation_id, type, name, address, maps_url)
rsvps (id, invitation_id, guest_name, attending, guests_count, message, created_at)
leads (id, name, wedding_date, contact, message, status, created_at)
```

`status` is always `'draft' | 'published'`. `locations.type` is always `'ceremony' | 'reception'`.

## Route structure

```
app/page.tsx                          product landing page
app/[slug]/page.tsx                   public invitation (renders WeddingInvitation component)
app/admin/page.tsx                    admin dashboard
app/admin/invitations/new             create invitation
app/admin/invitations/[id]/edit       edit invitation
app/admin/invitations/[id]/rsvps      view RSVPs for one invitation
app/admin/leads                       leads captured from the landing page
app/api/rsvp/route.ts                 POST — guest submits RSVP
app/api/leads/route.ts                POST — landing page "get a quote" form
app/api/invitations/[slug]/route.ts   GET — public invitation data by slug
```

`/admin/**` must be auth-protected. Never expose admin routes or link to them from public-facing pages.

## Key components

- `WeddingInvitation.tsx` — the reusable public invitation template. Takes a single `data` prop shaped like the tables above joined into one object. New visual themes must accept the same `data` shape so they stay interchangeable. Do not hardcode couple-specific content inside this component — it always comes from props.
- Landing page (`/`) — `app/page.tsx` holds only the composition (plus page `metadata`); each section is its own module in `components/landing/`: `SiteHeader`, `Hero`, `ExampleGallery`, `HowItWorks`, `WhatsIncluded`, `QuoteSection`, `Testimonials`, `Faq`, `SiteFooter`, with the shared pieces `SectionHeading`, `icons.tsx`, `Reveal`, `PhotoPlate`, `QuoteForm` and `cta.ts`. Every string of Spanish copy lives in `lib/content/landing.ts` (page copy) and `lib/content/site.ts` (contact details, WhatsApp link); the content module stores icon **keys** (`FeatureIcon`), never components, and `icons.tsx` maps them to glyphs. Interactive pieces are client components, so `app/page.tsx` itself stays a server component.
- Sample photos for the collection cards live in `public/examples/` and are wired through `galleryExamples[].photo` (`{ src, alt }` — the Spanish `alt` belongs in `lib/content/landing.ts`, never in the component). `ExampleGallery` renders them with `next/image` (`fill` + `object-cover` inside the card's 4:3 frame); an example with no photo yet falls back to the tonal `PhotoPlate`.

- The "Galería editorial de la preboda" card in `WhatsIncluded` closes with a three-photo strip wired through `preWeddingPhotos` (type `SamplePhoto` — the same `{ src, alt }` shape as the collection cards) and served from `public/pre-wedding/`; `next/image` (`fill` + `object-cover`) crops each original into the small `h-16` frames. Keep the array order: it is the left-to-right order on screen.

- Every card in `WhatsIncluded` closes with a static still of the real invitation (`SAMPLE_UI`), which is decorative and therefore wrapped in `aria-hidden` by `BenefitCard`. The music card's still mirrors the invitation's audio player — forest play button, track name, elapsed time and the gold waveform — matching the `Música sutil y personalizada` copy. Those short Spanish labels stay in the component on purpose: they describe product UI, not page copy.

- Hero mockup artwork is `public/header.png`, declared as `heroMockupPhoto` in the same content module (path + Spanish `alt`); `Hero` renders it with `next/image` (`fill` + `object-cover` + `priority`), so the 16:9 original is cropped to the card's portrait frame and the `Sofía & Mateo` demo overlay sits on the forest gradient over it.

- `Testimonials` renders `null` while `testimonials` is empty — never invent social proof; add real quotes to `lib/content/landing.ts` to turn the section on.

## Conventions

- All user-facing copy on the landing page and public invitations is in **Spanish**. Code, comments, and this file are in English.
- Internal navigation always goes through `next/link` (`<Link href="/...">`), never a raw `<a>` pointing at an app route — `Link` prefetches and keeps client-side navigation, while a plain anchor throws the App Router away and full-reloads. Gallery cards linking to a published invitation (`/${slug}`) and every `/admin/**` link are `<Link>` cases; the admin is never linked from a public surface. Keep a plain `<a>` for what the router does not own: in-page hash anchors (`#coleccion`, `#cotizar`), external URLs opened in a new tab (`wa.me`, Instagram) with `target="_blank" rel="noopener noreferrer"`, and non-HTTP schemes (`mailto:`, `tel:`).
- Slugs are auto-generated from `couple_a` + `couple_b` (e.g. "camila-y-sebastian"), kebab-case, with a manual override field in the admin form in case of collisions.
- Mobile-first: most guests open invitations from a WhatsApp link on a phone. Test every public-facing page at a 375px viewport before anything wider.
- Respect `prefers-reduced-motion` in all Framer Motion usage.
- Photo uploads go to Supabase Storage, not committed to the repo and not stored as base64 in the database.

## Working style

Build feature by feature, following whatever roadmap or phase the owner specifies in the conversation — don't jump ahead to later phases (e.g. self-service client editor, payments, multi-theme system) unless asked. Don't silently change the stack, data model, or design tokens above; if one seems wrong for a specific task, flag it and ask before deviating.
